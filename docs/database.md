# Database conventions

These rules apply to every migration. They exist because the product is
multi-tenant and handles money: most of them close a hole that is cheap to
avoid now and expensive to fix once real data exists.

## Workflow

| Task                        | Command                    |
| --------------------------- | -------------------------- |
| Start the local stack       | `npm run db:start`         |
| Stop it                     | `npm run db:stop`          |
| Create a migration          | `npm run db:new -- <name>` |
| Rebuild from empty          | `npm run db:reset`         |
| Regenerate TypeScript types | `npm run db:types`         |
| Lint the schema             | `npm run db:lint`          |
| Show URLs and keys          | `npx supabase status`      |

- `supabase/migrations/*.sql` is the only source of schema truth. Never change
  a staging or production schema from the dashboard.
- Migration files are named `<UTC timestamp>_<snake_case_description>.sql`, as
  generated by `npm run db:new`. Never edit a migration that has been merged;
  write a new one.
- After any schema change run `npm run db:reset` and `npm run db:types`, and
  commit the regenerated `src/types/database.ts`. CI fails if it is stale.
- Local studio: <http://localhost:54323>. Local mail catcher (signup and reset
  emails): <http://localhost:54324>.

## Tenancy and row-level security

- Every business table carries `hostel_id uuid not null` and has RLS enabled
  in the same migration that creates it. No exceptions.
- Policies resolve membership through `SECURITY DEFINER` helpers in the
  `private` schema rather than querying `hostels` or `profiles` directly,
  which avoids recursive policy evaluation:
  - `private.user_hostel_ids()`: hostels the user owns or staffs. Use it for
    reads and for writes staff may make.
  - `private.user_owned_hostel_ids()`: hostels the user owns. Use it for
    owner-only writes.
  - `private.current_user_role()`: the caller's role from their profile.

  The standard child-table policy is therefore:

  ```sql
  create policy "rooms: members read" on public.rooms for select to authenticated
    using (hostel_id in (select private.user_hostel_ids()));
  ```

- A select policy that relies only on a membership helper cannot see a row
  inserted in the same statement, so `insert ... returning` fails. When the
  inserting user is identified on the row itself (as `hostels.owner_id` is),
  test that column directly as well.
- Write `auth.uid()` as `(select auth.uid())` inside policies so Postgres
  evaluates it once per statement instead of once per row.
- The `anon` role has no table privileges in `public` (see the foundation
  migration). Signed-out users can read nothing.
- **Composite tenant keys.** RLS only checks the row being written, not the
  rows it points at. Every parent table exposes `unique (hostel_id, id)` and
  every child references it with a composite foreign key, for example
  `foreign key (hostel_id, room_id) references rooms (hostel_id, id)`. A row
  can then never reference a parent in another hostel, even if a caller
  supplies a foreign id.
- Every new table is added to the cross-tenant RLS test suite (E9-T1) in the
  same pull request.

## Functions and views

- **Multi-row writes are Postgres functions.** `supabase-js` cannot run a
  transaction across several calls, so anything that touches more than one
  row or table (allocate, transfer, bulk room generation, invoice runs) is a
  `plpgsql` function called with `rpc()`. Default to `security invoker` so
  RLS still applies inside the function.
- `SECURITY DEFINER` functions live in `private`, declare
  `set search_path = ''`, fully qualify every name, and receive an explicit
  `grant execute` to the roles that need them.
- **Views are created `with (security_invoker = true)`.** Without it a view
  runs as its owner and silently bypasses RLS.

## Data rules

- Money is `integer` paise. Never `numeric` rupees, never floating point.
- Calendar dates are `date`; instants are `timestamptz`. Business dates
  ("today", the billing month, overdue) are computed in `Asia/Kolkata`, never
  from the server's UTC clock.
- Derived state is never stored: bed occupancy comes from live allocations,
  an allocation is live from its dates, and invoice paid, partial, unpaid and
  overdue come from payments and the due date.
- History is never deleted. Rooms and beds are archived; allocations are
  closed; invoices and payments are voided with a reason.
- Tables with `updated_at` attach the shared trigger:
  `before update ... execute function private.set_updated_at()`.
- Full ID numbers are never stored: only the last 4 characters and a keyed
  hash for duplicate detection.

## Rooms and beds (EP-04)

- **Beds are generated, never written by users.** A room's active beds always
  equal its capacity. Triggers on `rooms` call `private.sync_room_beds` in the
  same statement as the insert or update: growing restores retired beds first,
  then adds the next labels (`101-A`, `101-B`...); shrinking retires the
  highest-labelled vacant beds and fails with hint `room_beds_occupied` when
  there are not enough. Users may only update `beds.status` and
  `beds.status_reason`.
- **Occupancy has one source.** `private.bed_is_occupied(bed_id)` answers
  "does this bed have a live allocation?". Every occupancy rule (capacity
  reduction, archiving, blocking) and the `bed_states` and `room_inventory`
  views go through it.
- **History blocks deletes.** Deleting a room cascades to its beds, but
  allocations reference beds, rooms and residents without cascading (the
  default `no action`), so a room with history can only be archived. The
  delete action reports this as "archive it instead".
- **Business-rule errors carry a hint.** Triggers raise `P0001` with a hint
  such as `room_archived`, `room_occupied`, `bed_occupied` or `bed_retired`;
  server actions map hints to plain-language messages.
- `create_rooms_bulk` inserts a whole range in one statement, so one existing
  room number rolls back the entire batch.

## Residents and allocations (EP-05, E6-T1)

- **ID numbers are never stored.** `residents` keeps `id_proof_last4` and
  `id_proof_hash`, an HMAC-SHA256 of `<type>:<normalised number>` keyed by
  `ID_PROOF_HMAC_KEY`. The key lives only in the app's environment; never
  rotate it once residents exist, or duplicate detection stops matching
  older records.
- **One person, one record per hostel.** Unique `(hostel_id, phone)` and
  `(hostel_id, id_proof_type, id_proof_hash)`. Identity columns (name,
  gender, date of birth, ID proof) are not updatable; residents are never
  deleted.
- **Status lifecycle** is enforced by `private.residents_guard_status`:
  active → notice or blocked; notice → active, vacated or blocked;
  vacated → active; blocked → active. A resident holding a live bed cannot
  be marked vacated, and vacated or blocked residents cannot be allocated.
  Every change records `status_changed_by` and `status_changed_at`.
- **Allocations have no status column.** An allocation is live when
  `private.today_ist()` is between `start_date` and `end_date` (inclusive,
  null end = open-ended). Partial unique indexes allow one open allocation
  per bed and per resident; composite keys keep resident, bed and room in
  the same hostel and the bed inside the named room. Closing an allocation
  sets `end_date` and `vacate_reason` together.
- `resident_directory` (security invoker) lists residents with their current
  room and bed, for search by name, phone or room.

## ID proof files (E5-T7)

- Private bucket `id-proofs`, 5 MB, PDF, JPEG and PNG only (enforced by
  Storage itself). Objects live at `<hostel_id>/<resident_id>/<file>`;
  `private.id_proof_path_allowed` lets members of that hostel read, upload,
  replace and delete, and nobody else. `residents.id_proof_path` is checked
  to stay inside the resident's own folder.
- Files are only ever served through 60-second signed URLs, created with the
  user's own session (`/residents/[id]/id-proof`). The upload action checks
  the real file type from its first bytes, not the name or declared type.

## Fees (EP-07)

Full rules are in the header of `supabase/migrations/20261011090000_fees.sql`;
in short:

- **Money is integer paise**, never a mutable balance. `fee_structures` (rates),
  `invoices` (a snapshot of what a month cost) and `payments` (append-only).
- **Rates.** At most one rate per sharing type covers any day (exclusion
  constraint). `set_fee_structure` closes the rate in force the day before a
  new one starts; re-entering a rate with the same start date corrects it; a
  rate cannot be set before a later one. Issued invoices never change.
- **Rent precedence.** The allocation's `rent_override`, otherwise the rate for
  the room's sharing type in force on the 1st of the billing month. A resident
  with neither is reported as unpriced, never under-billed.
- **Monthly billing** (`generate_invoices`, one statement). Each resident who
  held a bed on at least one night of the month gets exactly one invoice
  (partial unique index on `(resident_id, period_month)` for issued
  invoices). A full month costs the rate; otherwise
  `sum(rate × nights held) ÷ days in month`, rounded to the rupee, which also
  covers mid-month arrivals, departures and transfers on one invoice.
  Open-ended stays count to month end (rent is billed in advance). Future
  months cannot be billed; months and due dates follow Asia/Kolkata.
- **Corrections.** An invoice is voided with a reason (only when no live
  payment sits on it) and the month can be generated again for that
  resident. A payment is voided with a reason. Nothing is edited or deleted.
- **Derived status.** `invoice_balances` (security invoker) computes paid,
  balance and `due_status`: paid, overdue (past due with money owed, India
  date), partial or unpaid. `resident_balances` sums them per resident.
  Overpayment is rejected per invoice, under an advisory lock so concurrent
  collectors cannot overpay between them. Voiding an invoice takes the same
  lock, so a void and a payment racing on one invoice never both succeed.
- **Roles.** Owners set rates, generate and void. Owners and staff read fees
  and record payments.
- **Who recorded a payment** is snapshotted in `payments.recorded_by_name` by
  the insert trigger (clients cannot write it), because staff cannot read the
  owner's profile. `billed_months(hostel)` lists the distinct billed months
  for the fee filter; reading invoice rows would stop at the API's 1000-row
  cap.

### Reading lists through the API

PostgREST returns at most 1000 rows per request (`max_rows` in
`supabase/config.toml`, the same on hosted projects), silently. Anything
that can grow past that is paged (`.range()`), aggregated in the database,
or returned by a function, never read whole and reduced in the app. A page
that starts past the last row answers HTTP 416 (`PGRST103`); list pages
treat that as "go to the first page" (`src/lib/pagination.ts`).

## Dashboard (EP-08)

`supabase/migrations/20261011120000_dashboard.sql`. Both functions are
security invoker and derive everything at read time.

- `occupancy_trend(hostel, from, to, 'day' | 'month')`: occupied beds per day
  from allocation dates, so backdated changes rewrite history correctly. The
  bed count for a day is every bed not yet retired (or in a room not yet
  archived); bed creation dates are ignored because owners enter rooms on
  the day they start using the app. Months average bed-nights. Days after
  today are never returned; ranges are limited to two years.
- `dashboard_money(hostel, from, to)`: collected (live payments received in
  the range), billed (issued invoices for months starting in the range), and
  outstanding and overdue as of today across all months, so it matches the
  fee list.
